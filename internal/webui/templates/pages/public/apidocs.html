API

JSON API with the SSE envelope; every GET accepts application/json, text/event-stream. Errors are plain text. Null-safe: empty arrays, never null (except a repo's head).

Checks — reporting from external CI

External CI posts per-commit results without a user credential: a repo admin mints a scoped wct_ token, CI reports with it, anyone with read access views the combined state (the /checks page and the PR merge gate consume the same views). All checks GETs are no-store — sha-addressed does NOT mean immutable here; never cache them long. Errors are plain text: anonymous-denied reads get a real 401 with WWW-Authenticate: Bearer, authenticated-but-insufficient gets 403.

  • Auth. Reads need read access. POST …/checks/statuses/{sha} needs the repo write role or a wct_<id>.<secret> token with checks:write for this repo (send as Authorization: Bearer, Basic password, or X-Walgit-Authorization). Token mint/list/revoke need admin.
  • Report shape. POST …/checks/statuses/{sha} takes {context, state, target_url?, description?, started_at?, completed_at?} (strict: unknown keys are 400; state is one of pending|success|failure|error, anything else is 409; unknown sha is 404) and answers 200 with the full status record {sha, context, state, target_url?, description?, started_at?, completed_at?, creator, created_at, updated_at, version}.
  • Read shapes. GET …/checks/{sha} → {sha, state, total_counts, statuses} (worst-of: error > failure > pending > success; zero contexts ⇒ pending). GET …/checks/statuses/{sha} → {sha, statuses} (context-sorted). GET …/checks → {checks, more}.

Issues, labels, milestones

Threads with an immutable event tail. Reads need read access; create/comment/react need an authenticated principal with read access; patching honors author-or-triage per key; labels and milestones need triage. Threads are no-cache with a version ETag; the events tail is no-store. Unknown issue numbers are 404; anonymous on a private repo is 401.

  • Shapes. GET …/issues → {issues, more}; POST …/issues takes {title, body?} → 201 {thread, event}; PATCH …/issues/{num} takes {title?, body?, state?, labels?, assignees?, milestone?}. Reactions take {target_event_seq, content} (duplicate add is 200 with the summary, first add is 201). Attachment upload is multipart POST; bytes download at /{o}/{r}/attachments/{sha}/{name} (static contract, like release assets).

SDK: repo.issues.list/create/get/patch/comment/events, repo.issues.reactions.add/remove, repo.labels.*, repo.milestones.*.

Pulls and review

PRs ride the same numbering/thread/index family as issues. Reads need read access; opening, forking, and commenting need write; PR update honors author-or-triage; merge and head-delete need maintain (the merge gate also consults required reviews + checks). Merge, update-branch, and fork answer 202 with a task — poll …/merge/task (same SSE-attach envelope as …/api/tasks/{id}). Review reads need read access; submitting needs authenticated + read; review-request changes need triage; dismiss needs maintain; resolve honors author-or-triage.

  • Shapes. POST …/pulls takes {title, base_ref, head_ref, body?, fork?}; POST …/merge takes {strategy, commit_title?, commit_message?, delete_head?}; POST …/reviews takes {state, body?, commit_sha?, threads?} with state one of approve|request-changes|comment; thread anchors are {path, side, old_start?, old_lines?, new_start?, new_lines?, commit_sha?}.

SDK: repo.pulls.* (open, merge, mergeTask, updateBranch, deleteHead, fork) and repo.reviews.* (reviews, threads, requests, suggest).

Releases and assets

Release headers mutate by direct user action, so every version-keyed GET revalidates ( no-cache + store-version ETag — never a stale window). Reads need read access; upsert and asset upload/delete need write; release delete needs maintain. Asset bytes are immutable and content-addressed ( public, immutable, ranges, 304). Tags literally named latest or autodraft stay visible in the list but their single-GET is shadowed by the pointer.

Social: stars, watchers, forks

Counters mutate on every star/watch/fork, so GET …/social revalidates every read (no-cache + counter ETag). Starring needs an authenticated principal with repo visibility; unstarring always works for authenticated callers. Watch mutation lives here too: get needs auth, set/clear need auth + read. Forks are counted through the pulls fork task. Per-repo feature flags (General settings) can disable new stars/watches/forks (403 with a reason; unstar/unwatch always work; existing counts kept).

SDK: repo.social.* (star, unstar, counts) and client.socialTop.* (my / their starred lists).

Streams: notifications, collab, tasks

Three SSE surfaces share one envelope: send Accept: text/event-stream and the server holds the stream with named frames until the client disconnects. The tray and unread count are no-store (per-user private reads, authenticated; foreign notification ids are 404, never 403). Webhooks are repo-admin only and never return secrets ( secret_set instead). Task records (…/api/tasks/{id} and …/pulls/{num}/merge/task) answer JSON by default and attach as SSE under the same Accept header.

Identity: profiles, orgs, access

Profiles are self-or-admin writes; org reads admit anonymous on public hosts, member/team/invite writes need org owner, repo invites need repo admin, …/access reads need triage and replaces need admin with a version CAS (409 access.json changed under you on conflict). Invitations are token-bound: preview takes ?token=, accept binds to the authenticated subject. Roles resolve server-side — the UI reads one {role} from …/permissions instead of re-implementing the order.

SDK: client.users.*, client.orgs.*, client.invites.*, repo.repoInvites.*, repo.access.*.
