Threads

CI that lives in the repository.

A workflow is a file at .spindle/workflows/ci.yml. A branch push, a tag push, a pull request, a release, an issue, a schedule, an API dispatch or a button creates a run; registered runners execute each job in its own container; every job reports one check into the surface that already gates merges. No public marketplace to trust blindly — remote actions resolve only under an operator allowlist and are pinned and audited — a cache scoped to the run's trust class, no second service to operate — and no state outside the object store.

Quickstart

Two files, one runner, one check.

The workflow goes in the repository. The runner is a process you start once. The first push that carries the file triggers it — the workflow is read from the pushed commit.

1. Commit the workflow

Only .spindle/workflows/*.yml and *.yaml are read: one directory, no nesting, no fallback to another CI's directory. Each file is capped at 1 MiB. A file that does not parse creates no runs; its error is shown in the repository's Threads page while the other files keep running.

The file below is complete. It runs on every branch push and every pull request, inside a Go image, and reports the check threads/ci/test.

2. Start a runner

A host administrator mints a one-time registration token at /admin/runners, together with the runner's repository policy: every repository, or an allowlist of owner/name and owner/* patterns. On the runner host — Docker is required, and DOCKER_HOST names the daemon — exchange the token once and then serve:

Labels are exact strings matched as a subset: a job's runs-on must be contained in the runner's declared set. The hosted Linux labels (ubuntu-latest and the dated variants) map onto self-hosted + linux before matching, so a migrated workflow keeps its spelling; the Windows and macOS labels stay unmapped on purpose. Capacity 1 keeps one job per daemon, which is the isolation-preserving shape for untrusted code. The runner declares and then long-polls; a claim is a compare-and-swap on the queue entry, so any number of runners need no coordinator, and fetching is the heartbeat. A label may carry Forgejo's name:docker://image spelling (ubuntu-latest:docker://node:lts) to supply the image when the workflow names no container.image; lxc:// and host backends are refused at declare time.

3. Watch it

The repository's Threads page lists runs, the per-file parse errors and the Run workflow control. One run page shows jobs, runs-on, the runner, the check context, step results, artifacts and a live log per job. The commit page shows the same checks in its Checks panel, and the JSON API and spindle threads verbs return the same state.

The parser is strict. Substitution

A ${{ … }} span is validated at parse time against a closed vocabulary and expanded at run time. Only the following sites are substituted — anywhere else, the span is a parse error, never literal text that reaches a shell.

Every step site above also reads github.* (and the identical forgejo.*/forge.* aliases), the bounded github.event.* payload, runner.*, vars.* (repository over organization, sealed and masked), env.* and secrets.*. Inside a composite action's own steps, github.action_path is that action's directory, per nesting level; a workflow step, a job if: or an output template that reads it is a parse error. A job name and a concurrency group read github.* and inputs.* only (a job-level group also reads its matrix axes) — not env.*, secrets.*, runner.*, vars.* or outputs. The rule for a missing value has two halves:

  • An absent supported value expands empty: an unset env.NAME, a secret the run does not have (a fork run, a typo), github.actor on a run with no actor, or server_url/api_url with no canonical origin.
  • An undeclared output is an error: a steps.<id>.outputs.<name> or needs.<job>.outputs.<name> naming an unknown step/job or an output that was never published fails the step and names the reference.

Each site also has a fixed context availability set, checked at parse time and again at evaluation. A step field or a step if: reads every context above; a job if: reads github, vars, matrix, inputs, env, secrets and needs (no runner, no steps); a job name reads github, vars, matrix, inputs; a runs-on label and a timeout-minutes read github, matrix, inputs; run-name and a reusable caller's with: read github and inputs. A reference outside its site's set is a named error, never an empty value.

Expansion is one pass, so a substituted value is data, never a template: a secret whose body contains ${{ github.ref }} stays exactly that text. Secrets are masked in the log.

Triggers

Fifteen events, filtered by ref and path.

Filters use the documented Actions glob dialect — *, **, ?, + and an ordered ! — and paths narrows a run to the changed files. A push carries one kind of ref, so the two push filters are independent — a tags-only workflow never runs on a branch, and a branches-only workflow never runs on a tag. The GitHub-only events each read their workflow from the default branch (a pull_request_target reads the base tip) and name their own trust rule.

Push. branches matches branch pushes (refs/heads/<branch>) and tags matches tag pushes (refs/tags/<tag>) by exact name or pattern: * stops at /, ** crosses it, and ! negates in order. branches-ignore/tags-ignore are the exclusion spelling (naming both an include list and its ignore twin is a parse error). Naming neither ref filter fires on both kinds. paths/paths-ignore additionally select by the changed-file set — a push diffs its pre-image, and a path-filtered trigger never fires when no diff can be computed (fail closed). A merged pull request creates a push run for the base branch. A push authenticated by a job token creates nothing, branches and tags alike.

Tag runs. A landed tag starts a run; the tag name selects the tags globs. The run has no branch: github.ref is the full refs/tags/v1.2.3, github.ref_name is v1.2.3, and github.event_name stays push. A branch and a tag of the same short name are independent runs — one never cancels the other (Operations). A tag delete and a notes ref create nothing.

Pull request. branches filters the target and paths the merge-base diff. types is a closed vocabulary of what the pulls service emits: opened, synchronize, reopened, closed (including a merge), edited, ready_for_review, converted_to_draft, labeled, unlabeled, assigned, unassigned, milestoned, demilestoned. Omit types to fire on every emitted action. A same-repository PR runs the head commit's file, trusted, with secrets. A fork PR runs the base branch's file, untrusted, with no secrets and a read-only token, unless the repository opted in to send_write_tokens (maintain+, audited): then the fork token carries the scopes the file declares, still never secrets and never id-token.

Merge refs. Every pull request edge — the code edges (opened, synchronize, reopened, closed, edited, ready_for_review, converted_to_draft) and the metadata-only edges (labeled/unlabeled, assigned/unassigned, milestoned/demilestoned) — pins the server-computed merge commit of base and head, with refs/pull/<n>/merge as the run's ref and ${{ github.ref }}, with GITHUB_SHA and the check's commit reading the merge commit — so a failure that only exists after the merge goes red. The job's GITHUB_REF variable keeps the base branch, which is the documented job identity. If the merge conflicts, or the git reader cannot build one, the run falls back to the head commit and refs/pull/<n>/head and says so in the log. The workflow file is still the head's (same repository) or the base's (fork), never the contributor's file for a fork.

pull_request_target. The same edges, but the base branch's file runs with base secrets and a write token. It is off by default per repository; a maintainer enables it on the Threads page and the change is audited. Inside it, an actions/checkout naming a ref or another repository fails at plan time unless a second, separately audited switch (pr_target_allow_head_checkout) is on. A run: step can still fetch the head itself; that residual is why the default is off.

Repository dispatch. POST …/api/threads/dispatches with {"event_type":"deploy","client_payload":{…}} and the write role. The event type selects types; the payload is an object of at most 10 top-level keys, nesting at most 4 levels, 64 KiB encoded, exposed as github.event.client_payload.*. It runs the default branch only, and the answer is 202 {"runs":[…]}.

Following another run. workflow_run matches upstream workflow names (not globs), the upstream head branch, and requested or completed (completed when omitted). Its file comes from the default branch, and a chain stops at depth 3. An untrusted upstream (a fork PR) holds the follow-up at pending_approval until a maintainer approves; while that hold is pending, a cross-run artifact read is refused with 409 naming the parent run.

Repository and deployment events. create/delete fire for a branch or tag created/deleted by a push, with ref and ref_type in the payload. deployment fires when a job's deployment record is created; deployment_status when it is decided (pending, in_progress, failure). Both read the default branch's file, and a push authenticated by a job token starts none of them.

Release and issues. release fires on created/published/edited/deleted/ prereleased/released/unpublished; issues on its emitted lifecycle actions; and issue_comment on created. These runs read the workflow from the default branch tip, never from the tag or the commenter, and a release run still reports the tag's commit.

Dispatch. Typed inputs from the UI, the API (POST …/api/threads) or spindle threads run (with repeatable --input k=v). Types are string, boolean, choice, number and environment; inputs must match the declared schema or the call is 422.

Schedule. Five fields, UTC unless the entry sets a timezone:. Supported: *, numbers, ranges, steps (*/15, a-b/N), comma lists, JAN-DEC/SUN-SAT, the @daily-family macros, L/NW/#, and DL. A six-field expression or an invalid timezone is a parse error. Each entry can be disabled or enabled without a commit, and run now fires it manually — even while disabled; a backlog of missed ticks coalesces to one run and reports the count instead of replaying (Operations).

Structural fields — runs-on, container.image, environment — and workflow/job/container env do not take ${{ }}. A dispatch input can choose the environment name only if the job names it literally.

Jobs

Dependencies, matrices, one lock.

A job with no if runs only when every dependency succeeded. Failures propagate as skipped, never as a silent green. A matrix is the product of its axes plus include/exclude. A concurrency group admits one run at a time.

Propagation. A failed, cancelled or skipped dependency skips its dependents and records the reason. A true if runs anyway: always(), failure() or needs.test.result == 'failure'. if: false disables a job without deleting it.

Matrix. Product of the non-empty scalar axes, expanded in alphabetical axis order, values in declaration order. exclude removes a base cell that matches every pair of an entry; include merges into every surviving base cell it does not conflict with, and an entry that fits none becomes a cell of its own — so an include-only matrix is one cell per entry. Every cell gets its own job id, check context and MATRIX_<AXIS> variable. The result is capped at 256.

Fail-fast. On by default: a failed cell cancels its siblings. A job-level continue-on-error: true suppresses that, because the failure is tolerated: the job stays a failure, the run follows the other jobs, and dependents run with needs.<job>.result reading success.

Concurrency. One running and one pending run per group per repository, GitHub's rule. A newer run replaces the pending one (never a queue of stale commits); cancel-in-progress: true cancels the holder as soon as the new run is created. A workflow-level group belongs to the run, so sibling jobs do not serialize each other, and the run header names the group it waits for (pending_group) instead of showing a silent spinner. A group that cannot resolve is a parse error or a 422 — never a literal fallback.

The expression language

One evaluator serves every if: and every ${{ … }} site. It reads success(), failure(), always(), cancelled(), startsWith, endsWith, contains, format, join and hashFiles; github.* (and the identical forgejo.*/forge.* aliases), github.event.*, runner.*, vars.*, matrix.*, inputs.*, env.*, secrets.*, and steps.*/needs.* outcomes, conclusions and outputs.

The operators are !, ==/!=, ordered < <= > >= (numeric when both sides are numbers, text otherwise), value-returning &&/|| and parentheses. [ ] indexes a context (github['sha'], steps['build'].outputs['name']), and needs.*.result, steps.*.outcome and their output forms are list filters. && and || return an operand, so github.ref == 'refs/heads/main' && 'prod' || 'dev' renders a value.

hashFiles('**/go.sum') runs in the job container against the workspace (glob dialect, leading ! excludes, sorted deterministic hashing); it is available in step sites and job outputs, and a named refusal in a job if:. No match is the empty string; a walk over 1000 files or 100 MiB is a named error.

A job if: adds needs.<job>.result and needs.<job>.outputs.* and may read secrets.*/vars.* (empty on an untrusted run). An unsupported function or expression is a parse or evaluation error naming it — never a silently skipped job. toJSON, fromJSON, case and the rest of the hosted function set remain named parse errors.

Execution surface

One container, one workspace, your services.

Every job gets exactly one container and one workspace volume. Steps are docker exec invocations inside it, so the toolchain and network namespace persist. Services are sidecars on that job's network.

Image. container: names it; without one the runner's --image is used (default alpine/git, which carries git for checkout). The image must provide what your steps call — a distroless or scratch image has no shell.

Workspace. A per-job volume at /spindle/workspace. The runner mounts nothing else. Workflow-supplied volumes are refused: a bind mount is host filesystem access.

Services. Each entry is one sidecar, reachable at its key on the container port: postgres:5432, never a host port. The runner waits for a declared port or the image's own HEALTHCHECK; 60 seconds without readiness fails the job naming the service. A workflow can gate on the service's own readiness probe with docker's --health-cmd, --health-interval, --health-timeout, --health-retries and --health-start-period flags (they run inside the service container); a malformed probe is refused before the container is created. A registry credentials: block is refused by name: the pull identity is the runner's (its daemon config, an image mirror, or --registry-auth-file) and the password is piped on stdin, never argv or a log line.

Environment. Lowest to highest: runner built-ins, workflow env, job env, container env, step env, then secrets by name. Scripts read $GITHUB_SHA, $GITHUB_REF (the tag on a tag run), $GITHUB_REF_NAME, $GITHUB_WORKSPACE, $GITHUB_SERVER_URL, $GITHUB_API_URL and the rest; step fields also get ${{ }} substitution. $GITHUB_EVENT_PATH names the bounded event payload, and $RUNNER_OS, $RUNNER_ARCH, $RUNNER_NAME and $RUNNER_TEMP describe the runner. $GITHUB_STEP_SUMMARY collects markdown for the run page; $GITHUB_STATE is not provided (no pre/post hooks). $GITHUB_TOKEN and $FORGEJO_TOKEN alias the scoped job token. A step may write later steps' variables through $GITHUB_ENV and prepend to PATH through $GITHUB_PATH; protected names are refused by name.

Checkout. uses: actions/checkout runs inside the container and clones the run's exact commit with the job token, shallow unless fetch-depth: 0. fetch-tags: true, ref: and path: are supported; any other input is refused by name. Any job that pushes needs the full clone. The clone URL must be reachable from inside the container.

The options allowlist is small: --cpus, --memory, --memory-swap, --shm-size, --ulimit nofile=…, --init, --read-only, --user, --workdir, and docker's in-container --health-* flags. --cap-add, --device, --security-opt, every namespace flag and every mount are refused by default, at run creation and again at plan time.

Runner grants are the operator's. A workflow never widens its own isolation. Three knobs let a runner operator admit shapes for every job it takes: --container-privileged (admits --privileged and --cap-add), --container-valid-volume <glob> (admits a volume whose absolute host source matches), and --container-network (a user-defined network; host, none and namespace modes are refused). A grantable shape on a runner that did not opt in fails at plan time, naming the missing flag. A fourth, --docker-host, gives the job a docker endpoint (below). A runner that grants privilege or --docker-host refuses --allow-fork-runs, so an untrusted PR can never reach a widened runner.

No Docker socket. A job container gets no socket and no daemon by default, so docker build exits 127 with the daemonless remedy in the message. Build with kaniko (no privileges, no socket) or buildah on a host whose kernel allows user namespaces — the image is the workflow's choice, the capability is the host's. A runner whose operator passed --docker-host exposes an endpoint to the job container only; that job is root-equivalent on the runner, and such a runner never accepts fork runs.

Steps & actions

Built-ins, local and remote actions, images.

No public marketplace to trust blindly. uses: resolves to the built-ins, a repository-local action, a container image, or a remote action the instance's policy admits — resolved, pinned to a commit and a content digest, embedded in the job, and recorded. The setup helpers map their cache half onto the built-in actions/cache.

Composite actions. runs.steps expand in place; each run step must name shell:; in a local action an inner uses may only be another local action or docker:// (a fetched remote composite may nest another remote action). The caller's with: values become INPUT_<NAME> environment variables and ${{ inputs.* }} fields; an undeclared input is a named refusal. ${{ github.action_path }} is the innermost action's own directory, per level. Nesting is capped at 10 and cycles are refused.

docker:// steps. The image runs as its own container, gets the step environment and INPUT_*, and never the job token or a repository secret. Its $SPINDLE_OUTPUT is copied out and published under the calling step's id.

Outputs. echo "name=value" >> "$SPINDLE_OUTPUT" (or a heredoc: name<<EOF … EOF). Caps: 50 per step, 100 per job, 64 KiB per value. A malformed line, an unterminated heredoc, an empty or over-long delimiter, or a reference to an output that was never published fails the step naming it — never a dropped value.

Summaries and commands. Append markdown to $GITHUB_STEP_SUMMARY (1 MiB per step, 20 per job, 4 MiB joined) and the run page renders it through the sanitizing markdown renderer. Output lines of the form ::error::/::warning::/::notice:: become annotations (with file, line and title), ::group::/::endgroup:: fold the log, ::add-mask:: extends the mask, ::stop-commands:: suspends parsing, ::set-output:: joins the output namespace, and ::debug:: prints one debug line. An unknown command is a visible warning, not a silent drop.

actions/cache is built in and scoped to the run's trust class (Cache). Artifacts move files between jobs of one run; another run of the same repository is readable only behind the cross-run approval (Artifacts).

Remote actions: resolved, pinned, allowlisted.

A remote reference is default-deny. The server resolves it at run creation, refuses anything the policy does not admit, and otherwise pins the ref to a commit and hashes the action's files before embedding them in the job payload. The runner never reads a repository or the network for an action. The run header records action_loads (source, ref, commit, digest) and the same facts land in the log.

Execution forms: a composite expands like a local one, including ${{ inputs.* }}, github.action_path and nested remote uses: (depth 10, cycles refused); a JavaScript action (using: node20/node24) runs on the job image's Node and names a declared minimum — a missing or too-old runtime is a named failure, never a skip; a docker action runs a registry image or builds its Dockerfile on the runner host, and the job container still gets no docker socket.

No implicit credential: a remote action receives its declared inputs and INPUT_*, never the job token or a repository secret. Changing the bytes under a pinned commit is a refusal. Revocation is removing the allowlist entry — the next run refuses the reference by name, quoting the allowlist key and both remedies.

The three modes: deny refuses every remote action (an air-gapped instance); allowlist (the default) permits a mutable tag or branch only for an approved repository and requires a full commit SHA everywhere else; open accepts mutable refs anywhere — an explicit operator weakening. Every mode still pins the commit, hashes the content and records both.

Reusable workflows: a typed interface.

A job can call another workflow instead of declaring steps. The callee declares on.workflow_call: typed inputs (string, boolean, number, with required/default), declared secrets and outputs templates. Its jobs join the same run as deploy / release, with their own checks and logs.

with: is expanded once at run creation from github.* and the caller's inputs.*; an unknown input, a missing required one, or a value that does not parse as its declared type is a named refusal. secrets: is an explicit callee: ${{ secrets.SOURCE }} map or inherit; a same-repository callee with no block gets the repository's secrets, and a cross-repository callee gets none by default. inherit never crosses a repository boundary. permissions: is downgrade-only.

Cross-repository calls are owner/repo/.spindle/workflows/x.yml@<40-hex sha>: public on this instance, a full commit (never a branch or tag), explicit secrets only, and each call writes an audit record naming caller, callee and commit. Nesting is capped at 4 levels and a cycle is refused. Not supported, each a named refusal: a matrix caller, environment secrets inherited by a callee, and a needs. reference to a nested call's job.

Background and parallel steps.

background: true starts a step asynchronously while later steps run; wait: <id> (or wait-all: true) joins it and fails when it failed, cancel: <id> terminates it, and the job end kills every remaining background on every conclusion. Each runs in its own session and process group inside the job container (setsid must be in the image), so a kill reaches every child; the runner verifies none survived and fails the job rather than leaking it.

parallel: runs its members concurrently and reports them in declaration order. They share the workspace, so two members writing one file race. A member failure fails the group unless that member has continue-on-error. A background step needs an id; wait, wait-all and cancel are control keys, mutually exclusive, and are refused inside composite actions.

Secrets & permissions

Secrets are environment variables.

A repository secret is injected under its own name into every step of a trusted run. ${{ secrets.NAME }} is substituted too, and a whole-value env: entry is delivered by name so the value never reaches argv. The job token is automatic, short-lived and scoped to one attempt.

Writing. Settings → Secrets, or PUT …/api/threads/secrets/{name}. Write-only: the API returns names and timestamps, never a value. Names match [A-Za-z_][A-Za-z0-9_]{0,63}; values are 1 B – 64 KiB.

Reading. The value is an ordinary environment variable. ${{ secrets.NAME }} also works — as the whole value of an env: entry it is delivered by name, embedded in a script it is spliced and masked. Guard it: ${TOKEN:?TOKEN is not set} turns a missing secret into a clear failure instead of an empty string.

Masking. Best effort, server-side: exact substring replacement in log lines; values shorter than 4 bytes are skipped. Encoded or split values print. Never write a secret into an output or an artifact — both are data, not logs.

Fork runs. No secrets at all. The payload carries an empty set; a fork can never opt in by editing the file. A repository may opt in to send_write_tokens (maintain+, audited) so the fork run's token carries the scopes its file declares — never secrets and never an id-token, and the run page records the decision.

The job token. $SPINDLE_JOB_TOKEN always reads its own repository; $GITHUB_TOKEN and $FORGEJO_TOKEN are the same token under their familiar spellings, and an authored env: value of that name wins. permissions: is a closed vocabulary — contents, issues, pull-requests, deployments, id-token (plus read-all/write-all) — and it is also the token's platform-API authority: a read scope is the read role, issues: write is triage, contents: write or pull-requests: write is write, and deployments: write creates deployment records and their statuses for the run's repository (never the Threads operator surface). contents: write adds push. Any other scope is a named parse error, never an accepted-and-inert key. A fork is pinned to read. A protected ref still refuses it, because the principal is ci:<runner>, not the user. A push with it starts no workflow, so a workflow cannot rebuild itself forever.

Approvals and environments

A fork pull request from a first-time contributor is created pending_approval: jobs written, checks pending, nothing enqueued. A maintain or admin approves or denies on the run page (or POST …/api/threads/{run}/approve|deny). The gate applies when the actor has no previously merged PR in the repository; a same-repository PR is never gated. A workflow_run whose upstream run was untrusted is held the same way (approval_kind: workflow_run), and while that hold is pending a cross-run artifact read answers 409 naming the parent run. Nobody approves, nothing runs — there is no timeout.

An environment is a deployment target with up to six required reviewers (users or org/team, each needing write or more, checked when the environment is saved), a wait timer, prevent-self-review, a deployment branch/tag allowlist, its own secrets and its own non-secret variables. A job names one with environment: production; the run is created pending_approval, nothing is enqueued, and it starts only after every required reviewer (or a repo admin) approves and the timer elapses. A run from a ref outside the allowlist fails that deployment job by name. Environment secrets override repository secrets of the same name, reach only a trusted run with an approved deployment, and never reach a fork run; environment variables resolve as ${{ vars.NAME }} and override repository and organization variables of the same name. A job naming an undefined environment fails that job. A pending deployment is visible in the run list (naming the environment), notifies its reviewers and can be cancelled by anyone with write access.

Deployments serialize per environment. One deployment holds the environment's slot; every later one is recorded queued with one visible reason naming the holder, and is promoted when the holder reaches a terminal state. The queue is bounded at 100 waiters. Settings → Environments shows the protection rules, the deployments and the secrets/variables; the API is the same state (Deployments).

OIDC. permissions: id-token: write — or Forgejo's enable-openid-connect: true — on a trusted run supplies SPINDLE_ID_TOKEN_REQUEST_URL and a request token. POST a required audience for a five-minute RS256 JWT; the claim set is closed (iss is server.public_url, sub is repo:owner/name:ref:<ref>, :environment:<name> for an environment job or :pull_request, plus ref_type, ref_protected, job_workflow_ref, runner_environment and the run identity). write-all deliberately does not grant it, and an explicit id-token: none denies it.

Deployment records, statuses and the API.

Every deployment — a job that named environment:, or an external CI calling the API — is one record with its environment, ref, sha, creator, producing run/job, latest state and a bounded status history. States are queued, pending, in_progress, success, failure, error and inactive; a transition appends to the history and a terminal state releases the environment slot.

Authorization is the boundary: a repository write role may create, status and read. Artifacts, cache, schedules, retention

Files between runs; a clock that fires once.

Artifacts. Names are unique per run (letters, digits, ., _, -; up to 255 bytes). Paths are workspace-relative: exact file, directory, */? within a segment, ** across segments, or .. Only regular files; symlinks are not followed. The image needs find and tar. Caps: 256 MiB per file, 2 GiB per run, 1000 files per artifact.

v4 inputs. Upload: overwrite, include-hidden-files, compression-level. Download: pattern, artifact-ids, merge-multiple, and run-id. github-token and repository are refused by name — the job token is used and an artifact never crosses a repository.

Cross-run consumption. A run-id names another run of the same repository; it is never automatic. The consuming run is held at pending_approval until a maintainer approves (a fork run, or a job holding a repository/environment secret, is refused by name), and every cross-run read is audited. While a workflow_run parent hold is pending, the read is 409 naming the parent run.

List, download, delete. GET …/api/threads/{run}/artifacts lists (id, name, files, total_size, created_at, expires_at), GET …/artifacts/{name} returns one manifest, and DELETE …/artifacts/{name} needs the write role and reports bytes_freed. A closed retention window is a 404 on both reads even before GC runs; a manifest path that escapes the archive root is refused on extraction and on the ZIP writer, so a corrupt record cannot become a zip-slip.

Schedules. Default branch only; a process with the maintain role must be running. A CAS'd watermark fires each tick at most once, so a restart does not duplicate a deploy and a crash loses one tick rather than repeating it. Entries can be disabled and enabled without a commit, and run now fires one on demand — even while disabled. A backlog coalesces to one run and reports the count; it is never replayed.

Retention. Two operator windows. threads.retention (default 30 days) deletes a terminal run; logs, jobs and queue entries go with it. Checks do not, so an old required check still gates a merge. threads.artifact_retention is the artifact's own lifetime (created plus its upload retention-days, else the window), so an artifact can outlive the run that produced it. threads.keep_forever = true reclaims neither. A queued, running or pending-approval run is never swept, and neither is a run with a live job lease; the GC report names bytes per family and has a dry run that deletes nothing.

Cache: a workspace tree across runs.

What it does. actions/cache restores at the step and saves at the end of a green job (/save saves now, /restore never saves). Keys are exact; restore-keys (up to 10 prefixes) fall back to the most recent matching entry. The step publishes cache-hit — "true" only on an exact key match — and a miss is silent success unless fail-on-cache-miss is set. path must be workspace-relative (absolute paths and ~ are refused): point the tool at .npm, .cache/pip, GOCACHE and cache that directory.

Scopes and isolation. A default-branch run reads and writes default; another branch reads and writes its own branch and reads default; a same-repository PR reads and writes pr:<n> and reads its base; a fork's entry lives in pr:<n>:untrusted, which no trusted run reads; a tag run is read-only. A PR can never write a base-readable entry, and no PR reads another PR's cache. A merged PR's scopes are discarded. Content is addressed and integrity-checked, so a key collision can only select bytes the writer actually produced.

Limits. 1 GiB per entry, a 5 GiB repository budget (oldest-first eviction), 256 entries, and a 7-day idle window — all operator keys under [threads] (cache_max_entry_bytes, cache_max_bytes, cache_max_entries, cache_retention). The cache is derived data, never an artifact: the sweeper reclaims expired entries and orphaned payloads.

setup-* recipes. setup-node, setup-go and setup-python resolve as remote actions when the instance's policy admits them, and their cache: input is rewritten around this built-in pair. Without the action (or when it is refused), the same cache half is a recipe: npm_config_cache: .npm plus a cache of .npm; GOCACHE/GOMODCACHE under .cache/ plus both cached; PIP_CACHE_DIR: .cache/pip plus that cached. An unmapped setup action or cache manager is refused by name.

Operations

Tags, supersede, schedules, conformance.

What runs and what wins: a tag is its own ref, a newer push replaces older work, a schedule is an owned entry, priority orders the queue, and the engine's compatibility claims are gated.

Tag runs. A tag push is a first-class ref. The run header carries the full refs/tags/<tag>, github.ref_name is the tag, and the container's GITHUB_REF/GITHUB_REF_NAME carry the tag. A tag and a branch of the same short name are independent: separate runs, separate concurrency, separate supersede keys.

Supersede. A newer push to the same (workflow file, ref) cancels the older in-flight run; the superseded run reads cancelled, names its successor (superseded_by) and says supersede as the reason. A dispatch or a cron tick never supersedes, and a run that already ended is untouched. A workflow that declares a concurrency: group is never implicitly cancelled — the group is the explicit serialisation choice, so cancel-in-progress decides.

Rerun. A full re-run resets every job at a new attempt. Re-run failed (the run page or POST …/api/threads/{run}/rerun-failed) advances the attempt and re-queues only the failed jobs plus their transitive dependents; a successful job that is not downstream of a failure keeps its state, step results and green check. Image, container-option and environment gates are re-applied to every re-run job, and a gated deployment is held for a fresh approval.

Conformance. make parity runs the living matrix gate and the committed Forgejo corpus: every green row must name a test that exists, every gap must be planned, and the generated matrix must be fresh. It needs no docker and no network; the execution tier is opt-in (make parity-exec).

Schedules. The Threads page lists every entry with its next fire, its persisted watermark and any coalesced ticks. Each row has disable/enable (no commit, audited) and run now (allowed on a disabled entry, audited): spindle threads schedule list|enable|disable|run. A disabled entry keeps its watermark; re-enabling fires on the next due tick.

Pause and priority. spindle threads pause (or the page toggle, or POST …/api/threads/pause) stops the repository claiming jobs while in-flight jobs finish; every queued job says "CI is paused for this repository", and resume restores claims immediately. A manual dispatch may carry priority 0…10 (spindle threads run --priority 5); claim order is priority descending, then FIFO, and priority never bypasses an approval hold, a pause, a cap or a trust gate. spindle threads queue shows the live order.

Feedback. Checks carry annotations (level, file, line — stored and rendered, never changing the state), a per-workflow badge (GET …/threads/badge.svg?workflow=…&branch=…), and run-list filters (workflow, state, branch, event, actor; a bounded scan, with more saying whether it was capped). A failed run notifies watchers: one durable in-app notice per (user, run), plus one optional repository webhook POST — email is not offered on this instance. A single job can be cancelled without ending its siblings (POST …/threads/{run}/jobs/{job}/cancel); a non-forced cancel ends through the runner's ack, a forced one is terminal at once.

No silent queue. Every queued job names exactly one reason, in the order the read model checks them: the run's hold (an approval, or the repository's concurrency_cap), CI pause, a deployment queued behind an environment's serialization slot (naming the environment and queue position), a live needs: dependency, the pending concurrency group, a max-parallel matrix slot, then runner availability — no runner is registered, no runner matches labels …, fork runs are disabled on every matching runner, all matching runners are busy, waiting for a matching runner or a declared CPU/memory ceiling. The field is derived on read, so it changes the moment the cause clears.

A job-token push never starts a workflow, so a tag created by a CI job is silent by design. A branch and a tag named v1 never share a supersede key: the key includes the refs/heads/ or refs/tags/ prefix.

Fleet

Runners you can name, size and retire.

A runner declares its labels and capacity, then long-polls for work. Groups narrow who sees what, a one-job worker self-destructs, declared ceilings become exact queue reasons, and the fleet has ordinary operations: drain, resume, rotate, deregister.

Recipes

The shapes that cover most CI.

Test-only CI for Go

Tag a release

A landed tag starts a run of any workflow whose on.push.tags matches, so a release can be tag-triggered: on: push: tags: ["v*"] with if: startsWith(github.ref, 'refs/tags/v'). If you prefer one manual button, dispatch a version input and create the tag in the job — that tag push is silent, because it is authenticated by the job token. Both shapes are valid; pick one so a release does not run twice.

Build an image without a Docker socket

A job container never receives a Docker socket, so docker build has no daemon to talk to. Use a daemonless builder image. Whether it can create namespaces is a property of the runner host — the job cannot request --privileged or capabilities.

Migration

From a Forgejo workflow to Threads.

Most of a workflow translates mechanically, and the importer does it for you: convert, review the report, commit on a branch, run. What still needs a plan is the executable half of a remote action the importer cannot rewrite (the engine resolves and pins it under policy — keep that line by hand) and the host capabilities of a daemonless builder. The cache, artifacts, reusable workflows, pull-request triggers, run-name, defaults and max-parallel now translate.

The importer. Threads never reads .forgejo/workflows/ or .github/workflows/ — not as a fallback, not behind a flag. Migration is an explicit one-way conversion:

The command is read-only by default, never edits the source directory and never pushes. Everything it cannot express is named in the report and marked # UNTRANSLATED: at its own site; the command exits non-zero, and --apply refuses to commit unless you pass --allow-partial. --apply commits on a new branch only — never the current branch, never the default branch, never a force push.

The committed conformance corpus is the proof: all four real Weave/Scriobh workflows convert with zero refusals, parse, and plan. One construct still needs a manual rewrite: an object-valued matrix axis (matrix.os: [{name: …}]) — target axes are scalars, so use a scalar axis or one include object per combination. make parity keeps the claim honest.

The safe order

  1. 1

    Tests only

    Replace the custom checkout with the built-in one. Read-only, no secrets. This proves labels, image, checkout reachability and duration before anything can be damaged.

  2. 2

    Matrix and services

    Prove every cell and the database sidecar, still read-only.

  3. 3

    Artifact-producing jobs

    Build, upload, download and verify inside Threads. Still no credentials.

  4. 4

    Keep publishing where it is

    Move the credential only after the spindle job has produced the same bytes twice; run both once in parallel and compare digests, not logs.

  5. 5

    Retire the old workflow

    Only after a release shipped from Threads. The rollback is re-enabling the old file — one revert.
